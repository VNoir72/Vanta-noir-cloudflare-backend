# Order email delivery and controlled resends

Owner admin includes an Order emails panel with recent confirmation delivery problems, order-reference lookup and a reviewed resend flow. Staff cannot read the panel API, configure tracking or send copies. Changing a resend recipient does not change the order's original checkout contact details.

Each send now saves the Resend message ID alongside its outbox record. Signed delivery, delay, bounce, failure, suppression and complaint events update delivery metadata. Event handling preserves early callbacks arriving before message-ID persistence, ignores duplicates and cannot let an older delivery event hide a bounce or complaint. No open/click tracking is enabled. `sent` remains provider acceptance; `delivered` means recipient mail-server acceptance, not reading or inbox placement. Historical emails without saved provider IDs remain unconfirmed.

The scheduled worker tries once to register the configured EMAIL_WEBHOOK_URL using the existing Resend API key. It lists existing webhooks first, never changes unrelated endpoints, and leaves a setup-required state when permissions or network conditions prevent setup. A signing secret obtained through this flow is encrypted in private D1 metadata with an AES-GCM key derived from the existing runtime Resend key; it is never returned by an API. Rotating that runtime key requires reconnecting the signing secret. RESEND_WEBHOOK_SECRET is also supported as a runtime secret override.

When manual setup is needed, the owner can add the shown URL in Resend, select the six listed delivery events, and paste the webhook signing secret into the password field in Store admin. Existing email sending remains configured. Never enter an API key in that form or place either secret in source control. Tracking remains awaiting its first signed event until one arrives.

Resending requires owner authentication, same-origin POST, explicit recipient confirmation and a request UUID. Only verified paid orders qualify. An original pending/sending confirmation prevents another copy. Resends have a per-order ten-minute cooldown, request idempotency, endpoint rate limit and audit log. A copy enters the existing email outbox and normally sends on the next five-minute scheduled cycle. Nothing automatically re-sends a bounced or complained-about message, removes provider suppression, issues a payment/refund, or changes stock.

Validation covers automatic setup and insufficient key permissions, encrypted-secret non-disclosure, signature tampering and stale signatures, duplicate/out-of-order/early events, owner/staff/CSRF boundaries, unpaid-order rejection, queued-message and cooldown guards, concurrent resend requests, corrected recipients, preserved original order contact, and browser confirmation/retry/responsive layout behavior.
